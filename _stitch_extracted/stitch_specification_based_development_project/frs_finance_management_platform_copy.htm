1. Introduction

1.1 Purpose

This Frontend Requirements Specification (FRS) defines the client-application requirements for the Finance Management Platform. It is the companion document to the Software Requirements Specification (SRS v3.5), which specifies the backend API, data model, security, and operational requirements but explicitly excludes any user interface. This document closes that gap: every backend capability defined in the SRS is given a corresponding, traceable frontend surface here.

1.2 Relationship to the SRS

The SRS is the authoritative source for business rules, validation logic, security constraints, and data semantics. This document does not restate or override them; it specifies how a user reaches, understands, and operates each of those capabilities. Where the two documents appear to conflict, the SRS governs and this document is to be corrected.

Frontend requirements are identified with the prefix FE, numbered to mirror the SRS module they serve (e.g., FE-6.x covers the frontend for SRS Section 3.6, Transactions). This deliberate parallel numbering makes gaps visible at a glance.

1.3 Document Conventions

Priority follows MoSCoW (Must / Should / Could), consistent with the SRS. Items marked "Phase 2" correspond to SRS requirements deferred beyond initial public launch and are specified here only to the extent needed to avoid architectural rework later.

1.4 Intended Audience

●        Frontend engineers � implementation reference

●        Product / design � screen inventory, flows, and states

●        QA � basis for UI test plans and acceptance criteria

●        Security reviewers � client-side handling of tokens, credentials, and sensitive display data

●        Backend engineers � confirming API surface adequacy against real client needs

1.5 Scope

In scope: the primary end-user client (web and mobile-responsive), covering all user-facing capability defined in SRS Sections 3.1�3.14, plus the internal admin/support console (SRS Section 3.11) as a separate, separately authenticated surface.

Out of scope: visual design system specifics (colors, typography, component library selection), marketing site content, and native mobile applications. This document specifies what each screen must do and guarantee, not how it should look.

2. Overall Description

2.1 Product Perspective

The client is a stateless consumer of the platform's REST API. It holds no independent business logic of record: balances, budgets, conversions, and subscription status are computed and enforced server-side. The client's responsibility is presentation, input capture, validation feedback, and faithful representation of server-declared state � never the substitution of its own.

2.2 User Classes

User Class

Client Surface

Anonymous visitor

Public surface: signup, login, password reset, email verification

Free registered user

Full manual-tracking application; bank features visible but gated

Subscribed user

Full application including bank-linking and Gross Balance

Support agent

Internal admin console only (Chapter 9); no access to the consumer client

 

2.3 Platforms & Devices

●        Primary: responsive web application, functional from 320px mobile width through desktop

●        Modern evergreen browsers (current and previous major version of Chrome, Firefox, Safari, Edge)

●        Touch and pointer input both fully supported; no interaction may require hover alone

2.4 Design Principles

These principles derive directly from commitments made in the SRS and are binding, not stylistic preferences:

●        Financial honesty � never display a computed figure without making its basis available (source currency, exchange rate, as-of date). Derives from SRS FR-14.14, FR-6.5.

●        No dark patterns � cancellation, unlinking, and deletion must be no harder to reach than the actions that started them. Derives from SRS FR-12.8, FR-14.7, FR-13.3.

●        Read-only means read-only � bank data surfaces must make the absence of payment capability visually obvious, never ambiguous. Derives from SRS FR-14.9.

●        Never impersonate a bank � no screen may resemble a financial institution's own login. Derives from SRS NFR-9.7.

●        Free is genuinely free � gated features must be discoverable but must never obstruct or degrade free functionality. Derives from SRS FR-12.1.

2.5 Assumptions & Dependencies

●        The API exposes every endpoint enumerated in SRS Section 4.2, returning the consistent error schema required by SRS NFR-6.2

●        Bank-linking authentication occurs in a bank-hosted or provider-hosted flow the client redirects to, never renders itself (SRS FR-14.2)

●        Payment card entry occurs in a processor-hosted element (e.g., Stripe Elements), never in a form this client controls (SRS FR-12.3)

●        Subscription status is retrieved from the API as live state, never cached client-side as authoritative (SRS FR-12.9)

5. Screen Requirements � Banking & Subscription

These two modules are specified together because their behavior is interdependent: bank-linking is the subscription-gated capability, and subscription state directly determines what this surface presents.

5.1 Subscription & Billing (SRS 3.12)

ID

Requirement

Priority

FE-12.1

Client shall never gate, obscure, degrade, or interrupt manual-tracking functionality on the basis of subscription status (SRS FR-12.1). No upgrade prompt may block a free workflow.

Must

FE-12.2

Subscription is required only for bank-linking; the client shall present the paywall at the point of entry to that feature, not at signup or on the dashboard (SRS FR-12.2).

Must

FE-12.3

Card entry shall use a processor-hosted element; the client shall never render its own card-number input nor transmit card data through application code (SRS FR-12.3).

Must

FE-12.4

Subscription screen shall display current status, next billing date, and full billing history with downloadable receipts (SRS FR-12.7).

Must

FE-12.5

During free trial, client shall display days remaining and the date of first charge, without countdown pressure tactics (SRS FR-12.5).

Should

FE-12.6

On past-due status, client shall display a non-blocking banner explaining the retry schedule and grace period, and shall not restrict bank features until the API reports access as actually restricted (SRS FR-12.6).

Must

FE-12.7

Cancellation shall be self-service, reachable within two interactions from Settings, and shall state plainly that access continues to the paid-period end and that the account then reverts to free manual tracking rather than being locked (SRS FR-12.8).

Must

FE-12.8

Cancellation flow shall not require contacting support, completing a survey, or navigating retention offers as a condition of proceeding.

Must

FE-12.9

Client shall derive gating from live API-reported subscription state on each session and relevant navigation, never from a cached or client-computed entitlement (SRS FR-12.9).

Must

FE-12.10

Post-cancellation, previously linked bank accounts shall be presented as inactive with a clear explanation, and the client shall not imply that historical manual data has been lost.

Must

 

5.2 Bank Linking & Gross Balance (SRS 3.14)

ID

Requirement

Priority

FE-14.1

Banking screen shall support linking multiple accounts across multiple institutions, listing all linked accounts grouped by institution (SRS FR-14.1).

Must

FE-14.2

Client shall never render, proxy, or capture bank credentials; linking shall hand off to the bank-hosted or provider-hosted flow (SRS FR-14.2).

Must

FE-14.3

No screen, modal, or component in this client shall be styled, branded, or worded to resemble any financial institution's own login interface (SRS NFR-9.7). The handoff shall make clear the user is leaving this application.

Must

FE-14.4

Before linking, client shall present an explicit consent screen naming the connection channel in use � the bank directly, or the named fallback provider � and stating that access is read-only (SRS FR-14.10, Section 8.4).

Must

FE-14.5

Where a third-party aggregation provider is used as fallback, the client shall name that provider visibly at the point of linking; disclosure shall not be relegated to a policy document (SRS FR-14.10).

Must

FE-14.6

Consent screen shall require an affirmative, unchecked-by-default action; consent shall not be bundled into Terms of Service acceptance (SRS Section 8.4).

Must

FE-14.7

Gross Balance view shall display the consolidated total in the user's display currency, and shall list each linked account's balance in its own native currency alongside (SRS FR-14.4, FR-14.14).

Must

FE-14.8

Gross Balance shall display the exchange rate used and its as-of timestamp, with converted totals labeled as approximate (SRS FR-14.14, NFR-10.2, NFR-10.3).

Must

FE-14.9

Linked account detail shall show institution name, account type, masked account number limited to the last four digits, current balance, and recent transactions (SRS FR-14.6).

Must

FE-14.10

Client shall never display, log, or expose an access token or any credential material in the interface, in developer tooling output, or in error messages (SRS NFR-9.2).

Must

FE-14.11

All linked-account surfaces shall carry a persistent, unambiguous read-only indication, and shall present no control that could be mistaken for initiating a payment or transfer (SRS FR-14.9, FR-14.3).

Must

FE-14.12

Unlinking shall be available from each linked account, require confirmation, and state plainly that access is revoked and cached transaction detail purged (SRS FR-14.7).

Must

FE-14.13

When consent lapses, client shall present a clear re-authorization prompt on the affected account, indicate that syncing is suspended, and continue displaying last-known data marked with its as-of date (SRS FR-14.8).

Must

FE-14.14

Client shall display the last successful sync time per linked account, and surface sync failures without implying the underlying bank balance has changed (SRS FR-14.5).

Must

FE-14.15

Client shall distinguish linked-account data from manually entered data throughout the interface, so the two are never conflated (SRS FR-14.5).

Must

 

Interface Prohibition � Payment Initiation

No screen, control, label, or affordance in this client may suggest, imply, or provide a path to moving money into or out of a linked bank account. This is not merely an omission of a feature but an active design constraint: per SRS FR-14.3 and the SRS's Explicit Out-of-Scope Statement, the platform holds no such capability, and the interface must not create a user expectation that one exists.

7. Cross-Cutting Interface Requirements

ID

Requirement

Priority

FE-X.1

Every monetary figure shall render with an unambiguous currency indicator; no figure may rely on an assumed default currency.

Must

FE-X.2

Any converted figure shall be visually distinguishable from a figure in its original currency, with the original accessible alongside or on interaction (SRS FR-6.5, FR-14.14).

Must

FE-X.3

Client shall never round or reformat monetary values in a way that alters the precision returned by the API.

Must

FE-X.4

Where a historical rate was used for a past-dated transaction, the client shall present the rate date rather than implying a current rate (SRS NFR-10.4).

Must

FE-X.5

Where a rate is unavailable and an approximation was applied, the client shall label the figure as approximate rather than presenting it as exact (SRS NFR-10.4).

Must

 

7.2 Error Handling

ID

Requirement

Priority

FE-X.6

Client shall consume the consistent API error schema (code, message, field) and map field-level errors to their corresponding inputs (SRS NFR-6.2).

Must

FE-X.7

Client shall never surface raw stack traces, internal identifiers, or database errors to the user.

Must

FE-X.8

Where email, monitoring, or rate services degrade, the client shall continue presenting core functionality rather than failing wholesale, consistent with SRS NFR-4.3.

Must

FE-X.9

Network failures shall be distinguished from validation failures and from server errors, since the appropriate user response differs in each case.

Must

FE-X.10

Destructive actions that fail shall state explicitly that nothing was changed.

Must

 

7.3 Loading, Empty & Partial States

●        Every data-backed view shall define a loading state, an empty state, an error state, and a populated state � none may be left undesigned

●        Empty states shall guide the next useful action rather than merely reporting absence

●        Partial failure (e.g., one linked account failing to sync) shall degrade only that element, never the entire view

7.4 Forms & Validation

●        Validation rules shall mirror server-side rules; client validation is a convenience layer and never the authority

●        Requirements (e.g., password policy) shall be stated before submission, not revealed only through failure

●        Unsaved changes shall be protected against accidental navigation away

7.5 Confirmation of Consequential Actions

Actions requiring explicit confirmation, each naming the specific object affected: account deletion, category deletion with dependent transactions, transaction deletion, bank account unlinking (FE-14.12), subscription cancellation (FE-12.7), and account deletion (FE-13.7).

8. Non-Functional Frontend Requirements

8.1 Client-Side Security

ID

Requirement

Priority

FE-N.1

Must

FE-N.2

Bank connection tokens shall never reach the client in any form (SRS NFR-9.2); the client shall have no code path expecting them.

Must

10.1 Test Coverage

Area

Coverage Requirement

End-to-end coverage of signup/verification, transaction entry with currency mismatch, bank linking with consent, subscription purchase, cancellation, and account deletion

Verified that no manual-tracking capability is ever blocked by subscription state, in any status (trialing, active, past due, canceled)

Automated WCAG 2.1 AA scanning per build, plus manual keyboard and screen-reader validation of core flows

●        Every SRS functional requirement traced to either a frontend requirement or an explicit, justified 'no interface required' entry (Appendix A)

●        WCAG 2.1 AA conformance verified before public launch
