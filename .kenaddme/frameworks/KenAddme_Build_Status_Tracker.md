## How to use this checklist

- Tick an item only when the evidence exists and can be located, not when the work feels done.
- Record the owner and evidence reference next to each item; an unowned tick is not evidence.
- Mark an item `[~]` for not applicable where tailoring permits, and `[!]` where an approved exception covers it. Log the exception in the exception register below.
- A gate is passed when the evidence is complete **and** the named authority records a decision of Approve, Approve with conditions, Hold, Redirect or Terminate.

# Project Management Track

Source: Project Management Framework v1.1

## Gate 1 — Intake decision

**Stage:** Stage 1 - Strategic Intake and Opportunity Definition  
**Decision:** Authorise feasibility work or decline  
**Decision owner:** Sponsor for Class C, ratified in batch at the monthly Project Authority review; Project Authority for Class A and Class B

> **Exit criteria.** The need is real enough to investigate, an idea owner is identified, the work supports institutional or client value, and feasibility effort is justified.

**Required evidence**

- [ ] `Gate 1.01` Project idea / intake record: problem or opportunity, proposed outcome, beneficiaries, owner, urgency and known constraints
- [ ] `Gate 1.02` Current situation described with evidence that a problem or opportunity exists
- [ ] `Gate 1.03` Affected users, clients, services and institutional goals identified
- [ ] `Gate 1.04` Expected outcome stated without assuming a solution too early
- [ ] `Gate 1.05` Initial screening for legal, ethical, security, privacy, safety, financial and reputational concerns
- [ ] `Gate 1.06` Urgency, rough scale and project-versus-operations judgement recorded
- [ ] `Gate 1.07` Comparison against active commitments and resource capacity
- [ ] `Gate 1.08` Initial classification proposed (Class A / B / C) with reasons
- [ ] `Gate 1.09` Portfolio recommendation: proceed to feasibility, defer, merge, return or decline
- [ ] `Gate 1.10` Gate 1 decision recorded with approver, date and conditions
- [ ] `Gate 1.11` Expedited Gate 1/2 path used? If yes, record urgency justification, authority, maximum spend, time limit and stop authority (Section 4.6)

## Gate 5 — Continuation or exception decision

**Stage:** Stage 5 - Continuous Monitoring, Control and Corrective Action (recurring from Gate 3 to Gate 6)  
**Decision:** Continue, correct, rebaseline, escalate or stop  
**Decision owner:** Sponsor within tolerance; Project Authority beyond tolerance or for Class A

> **Exit criteria.** Forecast performance remains acceptable, or a credible recovery/rebaseline decision has been approved. If value has disappeared, risk is unacceptable or recovery is not credible, the project must be paused, redirected or terminated.

**Required evidence**

- [ ] `Gate 5.01` Status reporting running at the class cadence (Class A weekly review plus formal status fortnightly; Class B monthly with fortnightly team review; Class C monthly plus midpoint check beyond 20 business days)
- [ ] `Gate 5.02` Minimum status report content complete: overall status, achievements, next period, schedule, cost/resources, scope/quality, risks/issues, decisions required
- [ ] `Gate 5.03` Status colour supported by evidence, not by activity or an unexpired deadline
- [ ] `Gate 5.04` Tolerance position measured against approved cost, schedule, scope, quality and risk limits
- [ ] `Gate 5.05` Variance analysis with root causes, consequences and corrective options
- [ ] `Gate 5.06` Gate 5 trigger log maintained (escalation trigger, forecast tolerance breach, material change, rebaseline, funding release, supplier failure, recovery plan, critical dependency change, doubtful acceptance, or a call by Sponsor/Authority/assurance)
- [ ] `Gate 5.07` Gate 5 convened within 2 business days for a red condition and 5 business days for any other material trigger
- [ ] `Gate 5.08` Corrective actions implemented, affected plans updated and effectiveness verified
- [ ] `Gate 5.09` Rebaseline decisions retain original commitment, approved changes and current forecast
- [ ] `Gate 5.10` Gate 5 decision recorded with approver, date and conditions

- [ ] `G5.01` Service catalogue entry, named service owner and support model

- [ ] `G5.06` Root-cause analysis for significant or recurring incidents with tracked corrective actions

- [ ] `G5.11` Enhancements and changes processed through the same traceability, review, testing and release controls

## Appendix I — gate alignment and evidence reuse

| Project gate | Software checkpoint | Consolidation rule |
| --- | --- | --- |
| Gate 1 - Intake | G0 - Intake | Use one intake record, sponsor, feasibility screen and initial classification decision. |
| Gate 2 - Project Authorisation | G1 - Requirements Baseline | Combine when requirements and acceptance criteria are sufficiently mature. If G1 follows later, reuse the charter and add only the requirements evidence; do not repeat the business decision. |
| Gate 3 - Delivery Readiness | G2 - Design Readiness | Use one integrated readiness pack covering project baseline, architecture, security/privacy, test, deployment, assurance and operational plans. |
| Gate 4 - Release Readiness | G3 prerequisite and G4 - Release Readiness | G3 code-complete evidence is an engineering prerequisite. One G4/Gate 4 approval pack authorises release under the stricter approver set. |
| Gate 5 - Continuation / Exception | G3 or G5 evidence where relevant | Gate 5 is recurring or triggered project governance. Engineering or early-life evidence may support it; no duplicate gate is required solely because numbering differs. |
| Gate 6 - Closure | G5 - Operational Acceptance and G6 - Retirement/Closure | Use G5 evidence for handover. Use G6 when the project closes or a service is retired. One closure record may satisfy both where scope matches. |
| Gate 7 - Benefits | Post-implementation review evidence; no separate software gate | Use service measures and the software review as evidence for the single Gate 7 benefits decision. |

## Classification mapping

| Project class | Normal software class | Mandatory interpretation |
| --- | --- | --- |
| Class C - Small / Low Risk | Software Class 1 or Class 2 | Class 1 is permitted only for time-bound, non-production experimentation with no real personal, client-confidential or payment data. Any operational or production use is at least Class 2. |
| Class B - Standard / Medium Risk | Software Class 2 or Class 3 | Use Class 3 where personal/sensitive data, public exposure, finance/identity, material reputation, contractual service levels or significant recovery impact exists. |
| Class A - Strategic / High Risk | Software Class 3 or Class 4 | Use Class 4 for safety-significant, critical-infrastructure, large-scale restricted-data or mission-critical services. Executive governance and explicit residual-risk acceptance apply. |
